Software Requirement

A property, condition, or capability that must be exhibited by software to solve a real-world problem, automate business policies, correct shortcomings, or satisfy a contract/standard.

1.1 Definition of a Software Requirement

Canonical SWEBOK Text

Formally, a software requirement has been defined as [ISO/IEC/IEEE 24765]:

  • A condition or capability needed by a user to solve a problem or achieve an objective;
  • A condition or capability that must be met or possessed by a system or system component to satisfy a contract, standard, specification, or other formally imposed document;
  • A documented representation or capability as in (1) or (2) above.

This formal definition is extended in SWEBOK v4.0 to include expressions of a software project's needs and constraints.

Why Requirements are High-Stakes Work

Real-world software projects suffer primarily from two requirements-related failure modes:

1. Incompleteness

Stakeholder requirements and necessary details exist that are never revealed or communicated to software engineers.

2. Ambiguity

Requirements are communicated in a way that is open to multiple interpretations, with only one interpretation being correct.

Each software product requirement generally leads to many design decisions, each of which leads to many code decisions and test decisions. Consequently, missing or misinterpreted requirements induce exponentially cascading rework.

Role in Long-Term Maintenance

A maintainer receiving code without documentation can run it, step through it with a debugger, or perform static analysis to discover what the code does. However, code execution cannot reveal what the code was intended to do.

"A defect (often colloquially called a bug) is simply an observable difference between what the software is intended to do and what it does. The role of requirements documentation throughout the service life is to capture and communicate intent."
